# L3 盲测协议：验证「未参与建模者能否用骨架独立走通」

## 为什么必须有这一层

L1（法条文本）与 L2（案例同一性）都已脚本化，但它们**都不验证建模本身**：

- L1 只证明引用的法条是真的
- L2 只证明被引案号存在、两家解析到同一案件；
  **它不证明知识库对该案裁判要旨、事实、说理的归纳是对的**

知识库里真正稀缺的资产是「骨架挂接」——把判决书拆到诉请层、抗辩层、要件层、
证据层、程序层。这一层对不对，**商业法源没有判据，只能靠人（或独立模型）盲测**。

CQ 文档自己也写着这个边界：**CQ 保证覆盖度，不保证正确性**。
现有的实例验证报告 v1–v4 与真实案件序列 v1–v3 全部是**建模者自验**，
属于同一批人用自己的骨架验证自己——这是当前最大的验证缺口。

## 协议

### 选案（隔离变量是第一原则）

| 要求 | 理由 |
| --- | --- |
| **未被建模时看过的案子** | 已挂接过的案子，建模者记得答案，无法盲测 |
| 与已验证案由不同或案情独立 | 避免复用既有要素组掩盖结构缺口 |
| 可从法宝/元典取到原文 | 保证可复核，且案号能过 L2 |

建议先用元典 `yuandian_search_judicial_cases` 选案（支持按案由、法院、
裁判日期、援引法条过滤），选完即跑 L2 确认案号真实。

### 给盲测方的输入（关键是「不给答案」）

提供：
1. 判决书原文（或法宝/元典正文链接）
2. 现行骨架（类/关系/枚举定义）

**不提供**：
- 该案已有的任何挂接结果
- 建模者的攻防图、要素表、判定结论
- 任何暗示性说明（包括"这个案子应该能跑通"）

### 要求盲测方独立产出

按骨架层次给出：

| 层 | 要产出 |
| --- | --- |
| L1 主张层 | 本诉/反诉各自的 Claim 及其 claimType |
| L2 要件层 | 各 Claim 对应的 Element，及 I2 要素映射 |
| L3 抗辩层 | Defense 及其 defenseKind、objectionValue |
| L4 事实层 | MaterialFact / AdjudicativeFact 及 findingBasis |
| L5 证据层 | Evidence 与 EvidenceAdmissibilityFinding（三性独立节点） |
| L6 程序层 | ProcedureStage 及审级关系 |
| A 论证翼 | Issue / Argument / Attack / Preference |

### 判定

与建模者结果逐项比对，按三类归档：

1. **一致** — 结构成立
2. **分歧但可归因** — 如条号位移、枚举取值理解差异；登记为待裁决
3. **盲测方挂不上（骨架无落点）** — **最有价值的发现**，直接对应骨架缺口

历史上这类缺口确实存在过：真实判决书首次全量跑骨架时暴露了
「判项没有落点、缺 Judgment 类」（fix7 候选）。那次是建模者自己发现的；
盲测的意义是让**没有预设的人**来撞这些缺口。

## 纪律

- 盲测发现的问题**不得直接改骨架**：按争议 009，须走 12 夹裁决卡
- 形式修正（拼写、数组形态等不改建模决策的）可直接改并逐条列明
- 盲测报告落 09 夹（该夹已有外部评审跟踪笔记的先例）
- 盲测方与建模方**不得是同一人/同一会话**；用独立 LLM 实例时，
  须确认其上下文未包含本库挂接结果

## 局限

盲测只能发现「挂不上」与「挂得不一样」，不能证明骨架在法理上正确。
法理正确性仍须专业法律判断，任何自动化都不替代。
