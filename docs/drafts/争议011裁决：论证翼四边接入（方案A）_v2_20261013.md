## 1. 已采纳的四条关系

| 关系 | 原方案的定义域 → 值域 | 用途 |
|---|---|---|
| `usesScheme` | `Argument` → `ArgumentScheme` | 论证使用的图式 |
| `hasCriticalQuestion` | `ArgumentScheme` → `CriticalQuestion` | 图式的批判性问题 |
| `attackTargets` | `Attack` → `Argument/Assertion` | 攻击节点的目标 |
| `argumentAddresses` | `Argument` → `Issue` | 论证回应的争点 |

采纳的是四边方案，不删除 `ArgumentScheme`、`CriticalQuestion`、`Attack`，也不只先接前两条。

## 2. 版本与关联裁决

原 v1 拟单独发布为 v3.5.2；用户本轮选择与 010、012 同批，因此实际关联版本为 **v3.6**，不再承诺另发 v3.5.2。

`AppellateRequest` 若作为 `Assertion` 子类，是否满足 `Assertion` 值域要由实现的继承规则核验；不能默认只接受精确类名的校验器会自动处理，也不能据此不经决定随意加宽值域。

**实现差异登记：** v3.6 的 `attackTargets` 实际值域为 `[Argument, Assertion, Judgment]`，比本卡原方案多了 `Judgment`。争议012明确列出的三处扩展是 `judgmentOn`、`attacks`、`issueConcerns`，不含此边。本次如实记录该差异，不借补记动作另作一次值域扩展裁决。

## 3. 裁决理由与保留的代价

- 既有三个类缺少关系接入，四边方案补齐其图结构用途，不必新建同义类。
- 只接两边会让 `Attack` 继续孤立；删除三类则改变已有设计范围。
- 四边名称及端点沿用原候选，减少新命名带来的对接成本。
- 原卡“代价几乎为零”仅指新增类数为零；查询、继承处理、数据迁移与语义回归仍有成本，不能略过。
