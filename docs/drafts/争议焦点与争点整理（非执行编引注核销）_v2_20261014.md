# 【自撰】争议焦点与争点整理：Issue 节点建模，与要素表 isContested 字段的对接

一句话：**`isContested` 是一个布尔开关，`Issue` 是一个争议对象；前者告诉你"这里有分歧"，后者告诉你"分歧是什么、在哪一层、有没有被解决"——只做前者，图谱永远生成不了"本案争议焦点"。**

## 1. 这条解决什么问题

一期 11 夹《要素式审判与裁判文书要素表》已给出 `isContested`（是否争议）。这是一个**要素粒度的布尔标记**，它解决了"这一格有没有分歧"，解决不了：

- **分歧在哪一层**：是事实真伪之争（被告说没收到货）、法律适用之争（这算不算"交付"）、还是程序之争（这份证据能不能用）？布尔值分不出。
- **分歧是什么**："双方对款项性质有争议"——一个布尔值里没有"款项性质"这个**争议对象**。
- **有没有被解决**：争议可以被法院认定而终结、被自认而消解、被和解而放弃、也可能被遗漏（法院没回应）。布尔值只有 true/false。
- **焦点归纳本身在哪**：争点整理是一个**程序行为**（庭前会议、审理前准备），有主体、有时点、有输出。布尔值里没有它。

而"争议焦点"恰恰是裁判文书中**信息密度最高**的一段——"本案争议焦点为：一、……；二、……"。它是类案检索、裁判摘要、诉讼可视化的最佳入口。不建模它是巨大损失。

## 2. 是什么

**争议焦点（Issue / contested issue）**：当事人之间存在实质分歧、且需要法院作出判断的**问题**。

**三层争点**（本条的核心分类）：

| 层 | 争点类型 | 英文 | 争议对象 | 判断性质 | 典型表述 |
|---|---|---|---|---|---|
| 1 | 事实争点 | factual issue | `MaterialFact` 的真伪或取值 | 事实问题 | "被告是否于 2023 年 5 月收到货物" |
| 2 | 法律（归入）争点 | legal issue / issue of subsumption | 已认定事实是否满足 `Element` | 法律适用问题 | "该转账是否构成借款合同的履行" |
| 3 | 程序争点 | procedural issue | 程序行为的效力 | 程序问题 | "该证据是否逾期提交""本院是否有管辖权" |

**第三层常被漏掉，但它是上诉率最高的争点类型之一。** 本体必须支持。

**还有一类特殊的"混合争点"**：评价性要件的判断（"情节是否严重""是否合理期限"），既是事实问题又是法律问题。处理办法：`issueType = legalIssue` + `isEvaluative = true`，不单列第四类。

**争点的生命周期**（这是与布尔值最本质的区别）：

```
产生 (raised) → 归纳 (summarized by court) → 审理 (examined) → 消解 (resolved)
                                                              │
                          ┌─────────────────────────────────┼────────────────────────────┐
                          ▼                                 ▼                            ▼
                    法院认定 (determined)              自认/免证 (admitted)        和解/放弃 (waived)
                                                                                        │
                                                                                        ▼
                                                                                  未回应 (unaddressed)
```

**五种消解状态是本条最有复用价值的枚举。** 其中 `unaddressed`（法院未回应）是**最有质量监控价值**的状态——它是发回重审与再审的法定事由之一（原判决遗漏诉讼请求/未对争点作出回应）。

## 3. 提出者与年份（含中国法制度出处与现行条文）

**中国法制度出处（**均以现行文本为准**）**：
- 庭前会议与争议焦点归纳：《最高人民法院关于适用〈中华人民共和国民事诉讼法〉的解释》（法释〔2015〕5 号，2022 年修正）第 226 条规定，人民法院应当根据当事人的诉讼请求、答辩意见以及证据交换的情况归纳争议焦点，并就归纳的争议焦点征求当事人的意见；第 225 条第（五）项将归纳争议焦点列为庭前会议内容之一；第 228 条规定法庭审理应当围绕当事人争议的事实、证据和法律适用等焦点问题进行。【已核销：法宝+辽河中院全文双源一致】
- 要素式审判：《民事诉讼程序繁简分流改革试点实施办法》（法〔2020〕11 号）第 14 条要求对能够概括出固定要素的案件，制作"要素式裁判文书"，根据案件要素载明原告意见、被告意见、证据和法院认定理由、依据及裁判结果——**原告意见/被告意见并列，就是 `isContested` 与 `Issue` 的文书落点。**
- 遗漏诉讼请求的上诉与再审事由：《民事诉讼法》（2023 修正）第 211 条第（十一）项（原判决、裁定遗漏或者超出诉讼请求的，应当再审）；二审阶段的处理见《民诉法解释》（2022 修正）第 324 条（原审未审理判决的，二审调解不成发回重审）。【已核销：法宝+公开全文双源一致；2023 修正条号 211 未变】
- 精准识别：《人民法院第六个五年改革纲要（2024—2028 年）》第 29 条提出"健全完善案件、案号、案由体系以及**精准识别**工作机制"——争点识别是其技术落点之一。
- 刑事侧：《刑事诉讼法》关于法庭审理中审判长应当告知当事人有权对证据发表意见、法庭审理围绕定罪量刑的事实进行的规定，**条号待核实**。

**学理来源**：英美法的 issue identification / narrowing of issues 是案件管理（case management）的核心技术；德国民诉的"争执关系"（Streitverhältnis）与争点整理理论；中文文献中"争点整理"自 2000 年代随庭前会议制度引入。LKIF-Core 提供了 `Issue`（争议点）与 `Question`（法律问题）的区分，可直接对齐。

## 4. 核心结构

**`Issue` 字段设计**（一期已有 `Issue` 类，本条为其填充）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `issueId` | ID | |
| `issueStatement` | 文本 | 争点的自然语言表述（"被告是否已履行交货义务"） |
| `issueType` | 枚举 | `factualIssue` / `legalIssue` / `proceduralIssue` / `mixedIssue` |
| `disputedObject` | → `MaterialFact` / `Element` / `Subsumption` / `ProcedureAct` / `Evidence` | **争议对象**（多态，本条的核心字段） |
| `isEvaluative` | 布尔 | 是否涉及评价性要件 |
| `raisedBy` | → `Party` | 由谁提出 |
| `contestedBy` | → `Party` | 由谁反对 |
| `summarizedIn` | → `ProcedureAct` | **争点整理行为**（庭前会议、庭审） |
| `summarizedBy` | → `Court` | 法院归纳 |
| `courtSummaryText` | 文本 | 文书中"本案争议焦点为……"的原文 |
| `resolutionStatus` | 枚举 | `determined` / `admitted` / `waived` / `unaddressed` / `pending` |
| `resolutionBasis` | → `AdjudicativeFact` / `Admission` / `ProcedureAct` | 消解的依据 |
| `resolutionOutcome` | 枚举 | `forPlaintiff` / `forDefendant` / `partial` / `none` |
| `establishedInStage` | → `ProcedureStage` | |
| `concursWith` | → `Issue` | 与其他同类案件争点的一致（承接一期已有关系名） |
| `parentIssue` / `subIssue` | → `Issue` | **争点的层级分解**（此处是真树形，与第 9 条的程序链不同） |

**与 `isContested` 的对接规则（本条的关键交付）**：

| 情形 | `MaterialFact.isContested` | `Issue` |
|---|---|---|
| 双方对某事实项无分歧 | `false` | 不生成（或生成后 `resolutionStatus = admitted`） |
| 双方对某事实项有分歧 | `true` | **必须生成** `Issue`（`issueType = factualIssue`，`disputedObject` → 该 `MaterialFact`） |
| 双方对归入有分歧（事实无争议） | `false`（事实本身无争议） | **必须生成** `Issue`（`issueType = legalIssue`，`disputedObject` → `Subsumption`） |
| 双方对程序行为效力有分歧 | 不适用 | 生成 `Issue`（`issueType = proceduralIssue`，`disputedObject` → `ProcedureAct`） |
| 法院未回应某争点 | `true` | `resolutionStatus = unaddressed` |

**由此得到一条硬规则**：**`isContested = true` 是 `Issue` 的充分不必要条件。** 事实层无争议时，法律层与程序层仍可有争点。反过来，`Issue` 存在时 `isContested` 必须为 `true`（若是事实争点）。

**`IssueConsolidation`（争点整理）作为 `ProcedureAct` 的子类**（承接第 9 条）：

| 字段 | 说明 |
|---|---|
| `actType = issueIdentification` | 新增枚举值 |
| `issueSet` | → `Issue`（多值，本次整理的争点集合） |
| `isCourtSummary` | 布尔：是否为法院归纳的正式争点清单 |
| `partyConsented` | 布尔：是否征求并获当事人意见 |
| `issueCount` | 整数 |

## 5. 规模与现状活跃度

- **活跃度极高。** 争点整理是庭审实质化改革的核心，《人民法院第六个五年改革纲要（2024—2028 年）》明确提出"精准识别"机制要求；要素式审判与繁简分流改革把"原告意见/被告意见/法院认定"写进了文书模板（法〔2020〕11 号第 14 条）。
- **工程价值最高。** "争议焦点"是裁判文书中结构化程度最高、信息密度最大的段落，几乎是**天然的结构化数据**。相比全文相似度检索，争点级检索的精度提升是数量级的。
- **国际侧**：LKIF-Core 明确区分 `Issue`（争议点）与 `Question`（法律问题），可直接对齐本条的 `issueType` 三分；Carneades 用"争议命题"（issue proposition）驱动论证构建，与本条方向一致。**这是 CQ2 的正面答案：Issue 的抽象概念可复用（LKIF/Carneades 已有），具体争点的生成与消解规则必须自建（中国法特有）。**
- **现状判断**：主流法律 AI 产品几乎都做"争议焦点抽取"，但都把它做成**文本标签**（一段摘要），而不是**结构化节点**（有争议对象、有消解状态）。本条的价值正在于此。

## 7. 拿来能干什么（字段级 / 类级建议）

**保持一期已有 `Issue` 类，按本条填充字段；新增 `IssueConsolidation` 作为 `ProcedureAct` 子类。**
理由：`Issue` 已在一期类名清单内，无需新增；但争点整理**行为**必须独立（`ProcedureAct` 子类），因为它是有时点、有主体、有输出的事件，且要与第 9 条的程序时间轴统一。

**`MaterialFact` / `Element` / `Subsumption` 上的挂接**：
- `MaterialFact.hasIssue` → `Issue`（多值；`isContested = true` 时必填）
- `Element.hasIssue` → `Issue`（法律争点）
- `Subsumption.hasIssue` → `Issue`（归入争点，**这是最常见的法律争点挂点**）
- `ProcedureAct.hasIssue` → `Issue`（程序争点）

**新增关系**：
- `disputesOver`：`Issue` → `MaterialFact` / `Element` / `Subsumption` / `ProcedureAct` / `Evidence`（多态，本条核心关系）
- `consolidatedIn`：`Issue` → `IssueConsolidation`
- `resolvedBy`：`Issue` → `AdjudicativeFact` / `Admission` / `ProcedureAct`
- `hasSubIssue` / `hasParentIssue`：`Issue` → `Issue`（**此处是真树形**）
- `raisedBy` / `contestedBy`：`Party` → `Issue`（用一期的 `assertedBy` 表达"谁主张"的语义，另设 `contestedBy` 表达"谁反对"）
- `concursWith`：复用（跨案争点一致）

**给下游图谱的四条落点**：
1. **争议焦点自动摘录**：抽取文书"本案争议焦点为……"段，切分为多个 `Issue`，按 `issueType` 分类挂到 `disputedObject`。这是裁判摘要与类案检索的第一入口。
2. **类案争点检索**：按 `Issue`（`issueStatement` 的语义 + `issueType` + `disputedObject` 类型）检索，比全文相似度精确得多。**建议把争点检索作为类案产品的默认召回通道，全文检索作为补充。**
3. **遗漏争点预警**：`resolutionStatus = unaddressed` 的 `Issue` 列表直接输出——这是发回重审/再审风险清单，对二审与再审业务价值极高。
4. **争点—要件联动视图**：`Issue` 通过 `disputedObject → Subsumption → Element` 上溯到请求权基础，形成"争议 → 要件 → 法律效果"的完整链路。这是诉讼可视化产品最有力的一张图。

**schema 硬校验**：
1. `MaterialFact.isContested = true` ⇒ 至少一个 `Issue` 指向它（`issueType = factualIssue`）。
2. `Issue.resolutionStatus = determined` ⇒ `resolutionBasis` 必填。
3. `IssueConsolidation.issueCount` 必须与实际 `issueSet` 数量一致。

## 8. 坑与局限

- **坑一：把 `Issue` 当成 `isContested` 的别称。** 前者是对象，后者是标记。事实层无争议时仍可有法律争点（"双方对转账事实无异议，但对该款项是借款还是投资款有争议"——这是归入争点，不是事实争点）。**这是最常见的建模错误，会漏掉绝大多数法律争点。**
- **坑二：只做事实争点。** 实践中法律争点（归入、法律解释、规范竞合）与程序争点（管辖、逾期举证、证据能力）占比很高，且是上诉改判的高发区。**三类必须都建。**
- **坑三：争点归纳版本混乱。** 庭前会议归纳的争点、庭审中变更的争点、判决书最终写明的争点，三者可能不同。**建议 `Issue` 上存 `summarizedIn`（归纳行为）+ `finalInJudgment`（布尔，是否为判决书最终采纳的争点），并允许同一争议对象有多个历史 `Issue` 节点。**
- **坑四：与 05 论证本体重叠。** `Issue` 是**争议对象**，论证结构是**论证关系**。二者的接口是：一个 `Issue` 可以触发多个论证（正反双方），论证的攻击/击败/优先关系属 05 夹。**本条只建 `Issue` 节点与消解状态，不建论证图。** 两夹通过 `Issue.issueId` 做节点级对齐。
- **坑五：刑事争点遗漏量刑争点。** 刑事除定罪争点外还有量刑争点。承接 11 夹《四要件 vs 三阶层》"`SentencingFactor` 与定罪要素分离"的结论，刑事 `Issue` 应增加挂点 `SentencingFactor`。
- **局限**：`courtSummaryText` 的分句与争点切分精度依赖 NLP，短中期需人工校核。

## 9. 与其他条目的关系

- **本夹第 1 条**：`Issue` 主要挂在 L2 `MaterialFact` 上，消解后产生 L3 `AdjudicativeFact`。
- **本夹第 2 条**：归入争点是最高价值的 `Issue` 类型，`disputedObject → Subsumption`。
- **本夹第 3 条**：证据能力争议是程序争点的典型（"该证据应否排除"）。
- **本夹第 5 条**："某要件的举证责任归谁"本身就是一个争点。
- **本夹第 6 条**：事实真伪不明时，争点按 `burdenOfPersuasion` 消解。
- **本夹第 8 条**：自认使 `isContested` 转 false，对应 `Issue.resolutionStatus = admitted`。
- **本夹第 9 条**：`IssueConsolidation` 是 `ProcedureAct` 的子类，发生在庭前会议/审理前准备阶段。
- **11 夹《要素式审判与裁判文书要素表》**：本条是 `isContested` 的上层展开，两者通过"充分不必要"规则对接。
- **05 夹（论证本体）**：本条与 05 夹的交汇条。`Issue` 是争议对象，05 夹处理论证结构，两图通过 `Issue` 节点对齐。
